# 04 — Camera and capture filename patterns (P5's `filename_pattern`)

- **list_id**: camera_filename_patterns
- **version**: 1.1
- **authored**: 2026-08-20
- **owner**: P5 (injected) — the observation it produces is consumed by P6
- **consumer**: the caller-supplied `filename_pattern(filename) -> str | None` that P5's `extract_image` requires; a match produces one observation at `zone = filename`, no span, `reliability: possible`, and **no `signal_tier`**
- **match_field**: the filename with its final extension removed (the stem). P5 passes `file_row["filename"]`, which includes the extension; the matcher strips the last `.suffix` before applying any pattern. Patterns are anchored `^…$` against that stem.
- **normalization for matching**: No normalization of the stored value. Matching applies Unicode NFC and compares case-insensitively unless a row says otherwise; the emitted value is taken from the source filename, never rebuilt.
- **evaluation order**: Entries are evaluated **in the order listed** and the first match wins. Order matters: `IMG_20240115_103045` must be read as the Android timestamp convention, not as an Apple/DCF sequence. Anchoring alone already separates them, and a check asserts both the anchoring and the order.
- **return value**: Each entry carries **both** a `capture` (the regex group holding the substring of the real filename) and a `pattern_label` (the name of the convention), so the catalogue serves either reading of `filename_pattern`'s return type. Which one P5 wants is an open contract question — see `unc-return-value`, independently raised by the other version of this file as `unc-return-value-contract` — because P5 PLAN Task 15 writes `emit(zone="filename", raw=matched, …)`, making the return value the observation's `raw_value`. If `raw_value` must be source text (the safer reading of P4's RAW rules), return `capture`; if §2.6's field name "filename pattern" means the pattern itself, return `pattern_label`. Nothing else in this file changes either way.
- **sourcing**: **How to read the `verification` column, because it is not decoration.** Only five pages were opened and read directly while authoring these catalogues; three more were opened by the catalogues-finish agent, who supplied verbatim quotes. Everything else is marked `search_summary`: the fact came from a web-search result summary and the page itself was not retrieved. Those rows say `consulted` rather than `retrieved`, because claiming a retrieval date for a page nobody opened is exactly the kind of unearned confidence these catalogues exist to keep out of the product. A `search_summary` source is not worthless — it is how most of the vendor-prefix and manifest-name knowledge here was gathered — but it must not be quoted as if read, and a row that would be harmful if wrong should be upgraded before launch.

## Design basis

- §2.6: the image record stores "filename pattern" as one of its fields, alongside format, dimensions, EXIF and software metadata.
- §1.2 — the sentence that governs how this file is written: "A file called `Wash U.docx` may contain an unmistakable university application prompt; `Hw 5.pdf` may be a photographed homework page with no usable text layer; and **`IMG_4821.png` may be a screenshot of a receipt, application portal, conversation, code error, or research figure.**" The design's own example of this pattern is an example of a filename being *too weak* to conclude from.
- P5 SPEC Deferred: "Camera-filename pattern library | §2.6 | That filename pattern is an emitted field; `IMG_4821.png` is the design's example | The pattern set" — this file is the missing column.
- P5 SPEC E5: "E5 emits **no** photo/screenshot conclusion at all — `media type` is a Photos-domain fact (§3.11) and belongs to P6."
- P5 PLAN Task 15: `emit(zone="filename", raw=matched, label=None, reliability="possible")` — the filename observation is `possible`, carries no span, and carries no tier.

## Rules this list obeys

1. **A pattern names a naming convention, never a media type.** Every `pattern_label` in this file describes the convention that produced the string — "Apple/DCF camera-roll sequence", "macOS screen-capture default filename" — because that is a checkable property of the string. Whether the file *is* a photograph or a screenshot is `media type`, a Photos-domain fact, and P6's alone.
2. **A filename carries no `signal_tier`.** §2.6's tier table lists camera EXIF (1); capture time, GPS, sensor-shaped dimensions (2); exact display resolutions, PNG format, software metadata (3). Filenames appear in none of the three bands. This catalogue therefore cannot promote a filename into the hierarchy, and P5 emits the observation at `reliability: possible` with no tier.
3. **`IMG_4821` is the worked case.** It matches here as the Apple/DCF camera-roll convention. It is emphatically *not* a screenshot pattern — and it is also not proof of a camera, because iOS gives screenshots saved to Photos the same name, which is precisely §1.2's point. The row records both facts. `possible` is the design's own hedge and this file does not upgrade it.
4. **No date parsing.** Several conventions embed a timestamp. The patterns recognise the *shape* of the run of digits; no entry defines a date capture group, and nothing here parses, validates, normalises or emits a date. Date and academic-term extraction is §3.10's, deferred separately, and owned by P6.
5. **No unrestricted DCF form.** `^[A-Z0-9_]{4}[0-9]{4}$` is the standard's own generic shape and it is **refused** — it matches course codes (`MATH2010`, `ECON1001`), which is a catastrophic false positive in exactly this product's corpus. Only enumerated prefixes match. An independently written version of this list reached the same refusal.
6. **Absence is not evidence.** A filename matching nothing produces no observation. It is never a signal that the file is a screenshot, a photo, or anything else.

## Injection

`extract_image(..., filename_pattern=make_filename_pattern(load('04-camera-filename-patterns.json')))`. `filename_pattern` is a **required keyword with no default** (P5 PLAN Task 15) so that no pattern can reach `src/extractors/`. P5 PLAN's Global Constraints allow exactly one module-level regex in the whole package — `shape._LINE_BREAK_HYPHEN`, P4 D8's soft-hyphen repair — and Task 20 asserts by runtime introspection that no filename regex exists anywhere in `extractors`.

## Coverage note

v1 covers the conventions that produce the overwhelming majority of image filenames in a personal corpus: DCF vendor prefixes (Apple, Canon, Nikon, Sony, Fujifilm, Pentax, Panasonic, Ricoh, GoPro, DJI, HTC, Samsung), the Android and Pixel timestamp conventions, the two messaging conventions that explain stripped EXIF, and the macOS / Windows / Android screen-capture defaults. It is **not** a device database: per-model quirks, Olympus month-coded names, and localized screenshot prefixes are left to `uncertain` rather than guessed.

**Two coverage limits worth stating.** First, screenshot filenames are locale-dependent — a non-English macOS writes "Bildschirmfoto", "Capture d'écran", "スクリーンショット" — and v1 covers the English defaults only. Second, iOS assigns screenshots the same `IMG_####` name as camera captures, so **there is no iOS screenshot filename pattern to write**; the absence is real, not an oversight, and §1.2 is the design acknowledging it.
