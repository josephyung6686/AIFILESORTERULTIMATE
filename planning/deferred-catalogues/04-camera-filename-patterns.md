# 04 — Camera and device filename patterns (P5 E5 `filename_pattern`)

- **list_id**: camera_filename_patterns
- **version**: 1.0
- **authored**: 2026-08-20
- **owner**: P5 E5 (`extract_image`), through the caller-supplied `filename_pattern` strategy — the list itself is injected, never resident in `src/extractors/`
- **consumer**: `filename_pattern(filename) -> str | None`. A match is emitted as one observation at `zone = filename`, `label = None`, `reliability = possible`, **`signal_tier` absent**, `text_span` absent. P5 draws no conclusion from it; §2.6's photo/screenshot hierarchy is P6's.
- **match_field**: the filename **stem** — `file_row["filename"]` with its final extension removed. P5 passes the filename WITH extension, so stripping it is the adapter's first step. Stems only: `IMG_4821.png` and `IMG_4821.HEIC` are the same convention and must match the same row.
- **normalization for matching**: Unicode NFC and leading/trailing whitespace stripped, **for comparison only**; P4 RAW-1/RAW-2 keep the stored value byte-for-byte. No case folding is applied to the value — case-insensitivity is per-row, and every row in v1 is case-insensitive because a filesystem, a card reader or an export step may have changed the case of a name a camera wrote in upper case.
- **boundary rule**: **Every pattern is anchored `^…$` against the whole stem.** There is no unanchored pattern and no substring match in this catalogue: a substring match on `IMG_` would fire on `IMG_of_the_lease`, and a substring match on the word *screenshot* would let E5 approximate a media-type verdict (see `ref-screenshot-word-anywhere`). Catalogue 01's boundary rule solves the same problem for prefix strings; here anchoring solves it outright.

## Design basis

- §2.6 "For every supported image, the engine should store its format, pixel dimensions, file size, colour information where useful, content hash, perceptual hash, EXIF camera make and model, lens data, ISO, focal length, capture time, GPS, orientation, software metadata, **filename pattern**, and OCR output where needed."
- §1.2/§2.1 "`IMG_4821.png` may be a screenshot of a receipt, application portal, conversation, code error, or research figure" — the design's own example, and its own statement that the name settles nothing
- §2.6 "the system must not mistake the absence of EXIF for proof that an image is a screenshot. Messaging platforms and downloaded web images often strip metadata from real photographs. OCR text density is also not a reliable screenshot detector" — the two traps this catalogue is written around
- P5 SPEC, *Deferred*: "Camera-filename pattern library | §2.6 | That filename pattern is an emitted field; `IMG_4821.png` is the design's example | The pattern set" — this file is that pattern set
- P5 PLAN Task 15: `matched = filename_pattern(file_row["filename"])` … `emit(zone="filename", raw=matched, label=None, reliability="possible")` — the return value becomes `raw_value`
- P5 PLAN Task 20, the no-invention guard: "No resolution, no ratio and no filename regex appears anywhere in P5, and Task 20 asserts it by introspection."

## Rules this list obeys

1. **A pattern label names the naming convention, never the media type.** "Apple/DCF camera-roll sequence" and "macOS screen-capture default filename" name the software that wrote the name. No row says *photo*, *screenshot* or *scan*, because P5 SPEC E5 forbids E5 emitting a photo/screenshot conclusion and `media type` is a Photos-domain fact (§3.11) that belongs to P6.
2. **`family` is a grouping of conventions, not a verdict.** It records which kind of software writes the name — `camera`, `messaging`, `screen capture` — so a reader can navigate the table. P5 never emits it, and a `screen capture` family value is not a screenshot classification: §2.6 requires a hierarchy of signals and abstention on conflict, and a filename is not even in §2.6's hierarchy.
3. **No date is parsed, normalised, validated or emitted.** Several conventions embed a timestamp. Every such row recognises the *shape* (`\d{8}_\d{6}`) and stops there. §3.10's narrow date extraction is P6's, and `ref-bare-timestamp-shape` refuses the prefix-free form precisely so no reader is tempted.
4. **Absence is never evidence.** No row fires on a filename having no pattern, and `filename_pattern` returning `None` writes no observation at all. §2.6's first trap.
5. **Patterns are ordered and the first match wins.** Every pattern is anchored, so in v1 no two rows can match the same stem — `checks/check04.py` asserts that as an invariant, and asserts separately that `IMG_20240115_103045` resolves to the Android row and not to `cfp-dcf-img`.
6. **Cited prefixes, not a generic wildcard.** The one pattern that would raise recall most — DCF's generic four-character basename — is refused, because `FALL2024` matches it. See `ref-generic-dcf-basename`.
7. **P5 never holds this list.** It is injected as the `filename_pattern` strategy at construction. Nothing here may become a module-level constant inside `src/extractors/`; P5 PLAN Task 20 asserts by runtime introspection that no filename regex lives there.

## Injection

P5's `extract_image` takes `filename_pattern` as a **required keyword with no default**. The caller builds the matcher from this JSON — `extract_image(..., filename_pattern=make_filename_matcher(load('04-camera-filename-patterns.json')))` — and the adapter is responsible for (a) stripping the extension, (b) NFC-normalising for comparison only, and (c) trying rows in file order and returning on the first match. The compiled patterns live in the adapter, never in `extractors`: Task 20 walks `vars(module)` for every module in `src/extractors/` and a resident regex fails it.

## Coverage note

v1 covers the conventions for which a citable source was retrieved on 2026-08-20: DCF's six named prefixes, Nikon's two documented forms, AOSP's two camera format strings, macOS's screen-capture prefix, and WhatsApp's media-store form. It deliberately does **not** cover Canon's vendor prefixes, Pixel's `PXL_`, Android OEM screenshot forms, Windows' screenshot form, or any non-English macOS locale — each is in `uncertain` with the specific evidence that is missing. Recall is therefore known to be incomplete; that is the intended trade, because `filename_pattern` returning `None` costs one weak `possible` observation, while a wrong match puts a false convention name into the evidence record.
