# 06 — Citation and identifier patterns (P5's `find_structured_strings`)

- **list_id**: citation_identifier_patterns
- **version**: 1.0
- **authored**: 2026-08-20
- **owner**: P5 (injected) — the observations it produces are consumed by P6
- **consumer**: the caller-supplied `find_structured_strings(text) -> tuple[StructuredString, ...]` that E1 (PDF), E2 (DOCX), E3 (structured text) and E5's long-tail sibling all require. Each hit becomes one `StructuredString(kind, start, end)`, and P5 turns it into an observation whose `text_span` indexes into the `text_units` row its `container_path` names.
- **match_field**: the page text (E1), paragraph text (E2), or whole-file text (E3) that P5 hands the finder. Offsets are 0-based code points, half-open, as P4 D4 requires — and P4 RAW-1 then makes `raw_value` byte-for-byte the substring those offsets name, which is checked mechanically.
- **normalization for matching**: None. The finder matches the source text as given and returns offsets into it; it never rewrites, trims, or case-folds. Any normalization is `normalized_value`'s business and is mechanical only (P4 D8).
- **kind vocabulary**: P5 maps four kinds to a zone — `ZONE_BY_STRUCTURED_KIND = {url: link, email: link, doi: link, citation: reference_list}`. Any other kind "takes the zone of the region it was found in, because §2.2 names the class and the region says where it sits". This file uses the four mapped kinds where they apply and specific identifier kinds (`isbn`, `issn`, `arxiv`, `orcid`, `pmid`, `pmcid`, `ror`, `isni`, `rrid`, `handle`) elsewhere — deliberately, because a specific kind tells P6 what the string is while the zone-fallback keeps it located where it was found.
- **sourcing**: **How to read the `verification` column, because it is not decoration.** Only five pages were opened and read directly while authoring these catalogues; three more were opened by the catalogues-finish agent, who supplied verbatim quotes. Everything else is marked `search_summary`: the fact came from a web-search result summary and the page itself was not retrieved. Those rows say `consulted` rather than `retrieved`, because claiming a retrieval date for a page nobody opened is exactly the kind of unearned confidence these catalogues exist to keep out of the product. A `search_summary` source is not worthless — it is how most of the vendor-prefix and manifest-name knowledge here was gathered — but it must not be quoted as if read, and a row that would be harmful if wrong should be upgraded before launch.

## Design basis

- §2.2: the PDF extractor must preserve "headings, URLs, email addresses, DOI values, citations, identifiers, and other structured strings that may later support file facts."
- §2.2 again, on why location matters here: "A course code or university name found in a filename, title, or page-one heading is more meaningful than the same text appearing once in a reference list on page eighteen." P4's `reference_list` zone exists for that sentence, and the `citation` kind maps to it.
- P5 SPEC Deferred: "Citation and identifier pattern sets | §2.2 | DOI is named; citations and identifiers are named as classes | The patterns. **Date patterns are P6's (§3.10) and out of scope here**" — this file is the missing column, and it honours the exclusion.
- P5 PLAN Task 9: "`kind` uses section 2.2's own words. The PATTERNS are Deferred … so no pattern lives in `src/extractors/` and the finder is supplied by the caller."

## Rules this list obeys

1. **No dates. None.** §3.10 is P6's and is deferred separately: "Date candidates should be identified with explicit regular expressions… Academic terms such as `Spring 2025`, `AY 2024-25`, and `Michaelmas Term 2024` require dedicated patterns." Not one pattern in this file matches a year, a calendar date, or an academic term, and a check asserts that those five literals match nothing here. Where an identifier's own syntax embeds digits that happen to encode a date — arXiv's `YYMM` — the pattern matches the identifier's *shape* and no date is extracted, validated, or emitted.
2. **No gazetteers.** Universities, companies, course-code formats, institutions, labs and venues are §3.7's validated gazetteers — a different deferred row, owned by P6. Nothing here matches an entity name. `BUSIB 4300` matches nothing in this file.
3. **Checksums are mandatory where the standard defines one.** ISBN, ISSN, ORCID and ISNI all carry check digits, and the `checksum` column names the algorithm. A shape match without a passing checksum is **not** a hit. This is what keeps a 13-digit order number off the ISBN row, and it is the single biggest false-positive control in the file.
4. **A bare number is never an identifier.** Rows whose payload is only digits (`pmid`) require their label (`PMID:`) in the match. Without a label the string is unidentifiable and is left alone.
5. **P5 finds; P6 decides.** A hit is an observation, not a fact. Whether a DOI on page 18 means anything about the document is §3.7's positional weighting, and it is P6's.
6. **No personal-data patterns.** Government ID numbers, payment card numbers and phone numbers are refused below. They are §8.4 privacy surface and P7's, and a catalogue that manufactures them creates the exposure it would then have to protect.

## Injection

`extract_pdf(..., find_structured_strings=make_finder(load('06-citation-identifier-patterns.json')))`, and the same finder is passed to E2, E3 and the long-tail extractor — P5 PLAN Task 10 notes E1 and E2 share "the same injected `find_structured_strings`", so one finder built from this file serves every text-bearing extractor. P5 PLAN's Global Constraints permit exactly **one** module-level regex in the whole `extractors` package — `shape._LINE_BREAK_HYPHEN`, P4 D8's soft-hyphen repair — so no pattern in this file may be lifted into a module there, and Task 20 asserts it by runtime introspection.

## Coverage note

v1 covers the scholarly and bibliographic identifier families plus §2.2's three named string classes (URLs, email addresses, DOIs). It stops short of parsing **full bibliographic citations**: an APA, MLA, Chicago or IEEE reference is not a regular language, and a regex that tried would produce mostly-wrong spans that P4 RAW-1 would then faithfully preserve. What this file does instead is match **in-text citation markers** — the bracketed and parenthetical forms — which are regular, and leave full reference parsing to `unc-full-references`.

Also absent by design: national identifiers, VAT/EIN numbers, IBANs, ISRC/ISWC music codes, and container/tracking numbers. None is named by §2.2 and each would be either privacy surface or noise.
