## Result

**Refused.** The useful object here is a cycle in the file-neighborhood graph—presented variant → feedback → responding variant → approval—not an organizational template. Revision/version membership is already universal, and the cycle only becomes intelligible inside a named work, project or client engagement. The row cannot supply a creative-specific activation signal, a legal dimension, or a different privacy rule.

This is not a semantic quibble. The same bytes that appear to save the row defeat it: `_R2`, PDF comments, tracked changes, `APPROVED`, a response-to-reviewers table and a drawing revision block all prove iteration, but they do not prove creative work. Treating that structure as creative activation would misroute research manuscripts and construction drawings. Treating it only as a folder recommendation would split one work across round collectors. The design already provides the correct owners: universal `version_family`, P9 file relationships, the active project's template, and residual review when the target cannot be recovered.

## Node test, all three legs

### Detection signals

The schema anchor already owns intentional creative version families as one signal among linked assets, layers/artboards, briefs and deliveries. A separate round row would have to contribute something beyond that anchor. It does not.

There are four candidate observations: ordered same-stem variants, target-bearing feedback, a change that answers the feedback, and scoped approval. Together they can prove a cycle structure. But the proof is relational: no single file contains the whole situation, and none activates a template. CONNECTION assigns file-id relationships to P9 and explicitly bars schema/template ids from that graph. The correct implementation is a reviewable derived cycle over files already active in a project—not a second activation outcome.

The cycle is also domain-neutral. A research revision letter and a construction revision register have the same topology. Creative activation must instead come from the creative anchor's own evidence: linked assets, boards/layers, a brief, a delivery set or a production structure. Once that activation exists, the version cycle helps retrieval and grouping.

### Recommended dimensions

There are none legally: `creative` declares no fields, and a template may not branch on a proposed field. This is contract, not lack of imagination.

Under the anchor's unresolved adoption proposal, an honest project template might use `client → project → stage → artifact_type`. `R2` would then be a value of `stage` or a user-approved group label, never a new row. Round-first filing (`R1/`, `R2/`, `R3/`) makes the child meaningless without the project and scatters a single work. Date-first filing is worse: sent, feedback, export, approval and modification times are distinct.

### Privacy rules

Candid critique may name employees, reveal disputes, expose unreleased strategy or contain embargoed art. That makes the material potentially sensitive. It does not distinguish this row. The same confidentiality covers the brief, variants, approval and handoff within the engagement. A construction drawing's sensitivity belongs to its construction project; a manuscript review's to research. Protection follows the file and active schema, not the existence of a revision template.

## Feedback → variant → approval: what is provable

The following structure is supportable without inventing a node:

1. A presented file explicitly identified by content hash, attachment identity, or quoted filename.
2. A feedback record that identifies that target and contains requested or rejected changes.
3. A later variant in the same universal version family.
4. Explicit response notes or observed changes that align with the requests; semantic alignment alone remains model-supported and reviewable.
5. An approval record scoped to a purpose and tied to exact bytes or an unambiguous variant identifier.

Missing any link does not authorize propagation. Similarity cannot establish direction; chronology cannot establish causation; `approved` cannot establish scope; group membership cannot copy project or client facts. The graph may expose an incomplete cycle with evidence gaps. That is materially useful product behavior, but it is not a roster template.

## Fields and edges

`fields` and `proposed_fields` are empty. The row is refused; the schema is fieldless; and no new key is justified. `round`, `revision_number`, `approval_status`, `reviewer`, `feedback_type` and `variant` are tempting, but this pass refuses all six. Round/revision belong to universal version metadata or a possible future `stage` value; approval is scoped relational evidence; reviewer is non-destination authorship/role metadata; feedback type and variant are work-type/group labels. Minting keys here would turn a graph relation into a schema.

`collides_with`, `also_holds_with` and `role_split` are empty because the row does not survive. Multi-schema facts remain on fixtures: the photographed markup legally activates Photos; the drawing activates Construction; the response letter activates Research. These are not permissions for the Creative schema to widen its schema-level edges.

Career and Code were required neighbours. Neither receives an edge. A portfolio iteration may later be shown in Career, but the making record and the work sample are different evidence. Code review has the same cycle topology, which proves domain-neutrality; repository/root markers separate it, so it is not a same-evidence mutex collision with a refused creative row. Bare photo evidence likewise remains Photos unless creative anchor evidence exists.

## Residual coverage

- Independent Records: durable, readable versions or marked proofs with no broader group.
- Review Later: feedback whose target, role or approval scope remains unresolved.
- One-Off Images: isolated photographed markup without recoverable association.
- Protected Records: local-safe representation where candid comments or unreleased work require it.

The residual routes are not substitute domains. They are the safe outcomes when neither a project anchor nor a complete cycle can be recovered.

## Final recommendation

Keep `creative.revision-round` refused. Preserve revision membership as universal metadata, assemble feedback→variant→approval as evidence-bearing file-neighborhood structure, and show it inside the surviving creative project or client-engagement context. Do not freeze rounds as top-level folders and do not activate Creative from revision vocabulary shared across every knowledge-work domain.
