## The charge: the strongest case that this row should not exist

I put the case at its strongest before deciding, because on the roster evidence it very nearly
wins.

**`PCB layout` is verbatim an element of `engineering.json`'s `work_types[]` array.** It sits in
that list between `electrical schematic` and `bill of materials`, and the schema's own
`work_types_note` says those entries are "candidate VALUES of engineering_artifact_type … not
child schemas." Both of its neighbours in that array also have roster rows. So the prima facie
reading is not merely that this row is a work type — it is that a whole branch of the roster was
generated by walking a value enum, which is the 574's recorded failure reproduced at scale. If
that reading is right, this row's detection signals, dimensions and privacy rules are the
engineering default's with a narrower subject, and the node test's second refusal clause applies
exactly: refuse when "the only 'difference' is work types or file extensions."

The subsidiary charges, each of which had to be answered separately:

- **A file format.** `.gbr`, `.drl`, `.brd`, `.kicad_pcb`, `.PcbDoc` — a reasonable reader could
  say this row is the CAD-file extension list wearing a purpose. `SOURCE_TYPES` and extensions are
  not nodes.
- **A lifecycle stage.** "Released for fabrication" is a state of a board design, and
  `lifecycle_stage` is already a proposed field on the schema. A row that is a stage is a value.
- **A document type.** "Gerber" names a format; "fab package" names a bundle of document types,
  not one.
- **A duplicate of a neighbour.** `engineering.electrical-schematic` covers the same circuit, the
  same design item, the same tool, often the same project directory.
- **An organisation name.** JLCPCB, PCBWay, OSH Park, a contract manufacturer — never-alone
  evidence, and a row whose recognition leaned on a vendor name could never activate honestly.
- **A row defined by an absence.** Not applicable; nothing here is "engineering minus mechanical."

## Defeating it — the node test, all three legs

The charge is defeated on **one clause of the roster hint**, and only that clause: the row is
described as "The physical realisation of a circuit on a board, **and the manufacturing package
produced from it**." That second half changes the object from an artifact type to a **released
deliverable** — a multi-file, machine-generated set filed as one unit at one fabrication revision.
Under the narrow reading (a `.kicad_pcb` is a CAD model of a different flavour) the row must be
refused; that reading is preserved as **NJ-PCB-4** rather than argued away. Under the wide
reading, two of the three legs pass.

**Leg 1 — detection signals differ, and differ in kind. PASSES.**
Every one of the schema's ten deterministic signals keys on a *human-authored control structure*:
a title block, requirement rows with a verification-method column, a technical-data-package
manifest, a change disposition, a BOM parent/child relation, an analysis inputs/results pair, a
verification matrix, a prototype configuration record. **Not one of them fires on a copper-layer
Gerber.** That file has no title block, no approver, no requirement identifier, no revision slot
and no prose at all — it is a coordinate-format directive, a unit directive, aperture definitions
and coordinate blocks. The relation this row owns is a **layer-role vocabulary distributed across
a sibling set** (copper by stack position, solder mask, legend, paste, outline, drill) joined to
at least one plain-text coordinate-format or tool-definition header. That structure family exists
nowhere else in the engineering schema, and the schema's signals are structurally incapable of
seeing it. This alone satisfies CONNECTION's test.

**Leg 2 — recommended dimensions differ, in a direction the schema anticipated. PASSES.**
The default ends `… → lifecycle_stage → engineering_artifact_type`. Applied here, a six-layer
board's release opens roughly thirty artifact-type leaves — one per layer and program — each
holding a file that cannot be fabricated or read alone. That is the direct inverse of `00`'s rule
that "a parent dimension should provide the context required to understand the child." This row
therefore **drops** `engineering_artifact_type` and **promotes** `revision_or_baseline`, which the
schema proposes as `destination_eligible: false`. The promotion is not a preference: the schema's
own justification for that FALSE says a specific released-baseline template may later justify a
different order while the schema default does not. A board release is that template — the
fabrication revision *is* the deliverable's identity, the thing a fabricator is quoted against and
the thing a spin supersedes. Researched order: `project → design_item → revision_or_baseline`.

**Leg 3 — privacy rules differ. FAILS, and the row says so.**
Both sides are `potentially_sensitive`, and the two-value vocabulary cannot express the real
difference — that a complete package is a *reproduction recipe* (artwork + drill + stackup + parts
list is enough for a third party to have the board built) rather than a description. Handling
classes are P7's and no threshold or class is asserted. The row rests on legs 1 and 2 and does not
pretend to a third.

The subsidiary charges fall out of this. The **format** charge is answered by the never_alone list
and by `00`'s requirement to treat "the file extension as a routing signal rather than an
assumption about meaning" — `.brd` and `.net` are reused by unrelated formats and real drill
programs arrive as plain `.txt`, which is why `A2409-CTRL_RevD.TXT` is a file example. The
**lifecycle-stage** charge fails because a prototype spin produces a structurally identical
package with no release marking anywhere, so the stage token is neither necessary nor sufficient.
The **vendor-name** charge is answered by making the vendor the collision fixture.

## The collision fixture

**`Your PCB order A2409-1183 has shipped.eml`** — a fabricator's confirmation naming the order
number, layer count, board thickness, surface finish, quantity, unit price and ship date, with an
invoice attached. It is denser in board vocabulary than any Gerber and it comes from the most
board-specific sender imaginable. It is not this row's evidence. **What discriminates it:** it has
a price/quantity/order-number structure and **zero coordinate, aperture, tool-diameter or
layer-artwork data**, and the board's own filename stem appears nowhere. It routes to `Receipts
and Confirmations`. This fixture is why "a fabricator's name alone" is a `never_alone` line: a fab
house appears as a vendor on a purchase record far more often than as the recipient of a release —
the same role ambiguity `00` identifies for a university name.

Second fixture, sharper on geometry: **`Front-Panel_A2409_Rev2.dxf`**, a mechanical panel drawing
with named layers, coordinates and cutouts positioned to match the board's connectors, sharing the
board's project token. Discriminated by its layers being *draughting* layers (dimensions, cut,
engrave) rather than a copper/mask/paste stackup, and by the absence of any drill tool table or
aperture definition. It belongs to `engineering.cad-model`.

## Files considered and rejected

- **A firmware `.hex` or `.elf` in the release directory.** Real, common, and *not* this row's:
  its evidence is a build target and load address. It is a collision with
  `engineering.embedded-firmware` and `code`, not a member of the package.
- **A component datasheet PDF** pulled from a distributor. Received reference material about a
  part, not a definition of a board. `engineering.standards-library` / `Reading Inbox`.
- **A SPICE simulation deck for one sub-circuit.** Structurally an analysis with inputs and
  results — the schema's own signal 6 and `engineering.simulation-analysis`. Nothing here
  discriminates it that the default would not.
- **A fabricator's capability datasheet** ("6-layer, 1oz, ENIG, min trace 0.1mm"). It looks like a
  stackup document and is the strongest false positive after the order email. It describes what a
  *vendor can do*, not what *this board is*; kept only as a `needs_llm` line.
- **An assembly-house feeder setup or machine program.** Derived from the placement table but
  parameterised by a specific machine and run. Execution, therefore `manufacturing`.
- **A phone photo of a populated board on a bench.** Kept in spirit as `board_render.png`, but the
  bench photo specifically was rejected as a file example because its correct destination is a
  photo residual and it teaches nothing this row owns beyond what the render already teaches.
- **A `.ics` for a design-review call about the board.** A `SOURCE_TYPE` and an event; the schema
  default handles it, and it discriminates nothing.

## Neighbours considered that did **not** get an edge

- **`engineering.change-order`** — an ECO that supersedes a board revision is real, but the
  discriminating evidence (affected item, current/replacement revision, disposition) is the
  schema's signal 4 and the sibling's whole definition. Adding an edge would give one fixture
  three claimants.
- **`engineering.verification-validation`** — an electrical test report on a board. Its trace to
  requirement identifiers is what makes it that row's; this row's DRC report has no requirement
  trace at all, so the two never contest the same bytes.
- **`engineering.industrial-design`** — enclosure appearance work shares a product but no
  structure.
- **`manufacturing.tooling-fixture`** — a stencil is arguably tooling, but the *stencil artwork* is
  a paste layer in the release and the *physical stencil asset* is the sibling's; they are
  different objects, not competing readings of one file.
- **`business_operations` / `construction_property`** — the schema row already carries both as
  co-activations; nothing in a board release adds a claim.
- **`also_holds_with`: empty by contract.** It is a schema-row relation and this is a template.
  Every multi-membership I found was either same-schema (the fab drawing) — which is a collision
  plus a grouping question, never an `also_holds` — or already covered by the schema's five edges.
- **`role_split`: empty, and this is the interesting refusal.** The split this material wants is
  the board as a *designed item* against the board as a *produced asset*
  (`manufacturing.asset-register`). A `role_split` requires the two sides to hold different field
  **keys**, and under PR-6 neither side declares any field, so writing one would name a
  distinction the vocabulary cannot express. It lives in the manufacturing collisions instead,
  keyed on build-instance identity.

## `proposed_fields` — empty, deliberately

Three keys were genuinely tempting and all three were refused:

1. **A layer role.** It is a candidate *value* of `engineering_artifact_type`, already carried in
   `work_types`. Minting a key for it would rebuild the artifact-type slice the charge just
   defeated.
2. **A reference designator.** The worst `never_alone` on the node: `R12`, `C7`, `U3`, `J1` are
   also room numbers, citation labels, seats, grid cells and spreadsheet cell references. Evidence,
   never a key, and certainly never a folder level.
3. **A fabrication revision.** This is exactly the schema row's existing `revision_or_baseline`
   proposal. The brief requires reusing an existing proposal over minting a variant, so the row
   references it and argues its destination-eligibility exception in `template.why`.

`fields: []` for two independent reasons — PR-6, and the rule that a template never copies its
schema's list. `dimension_order` is likewise empty because a dimension order may only name fields
the schema declares; the researched order is stated in `template.why` so it is not silently
encoded before its keys are legal.

## Sparse-file discipline

Four of the thirteen examples carry `group_without_copying_facts: true`: `A2409-CTRL.PcbDoc`
(unreadable binary whose stem matches a neighbouring release — the stem must not become a fact),
`board_render.png` (no EXIF, no text, sits beside a release it does not name), the fabricator's
shipping email, and `Front-Panel_A2409_Rev2.dxf` (shares the project token, is not the board).
Each is the `HW 3.pdf` of this node from a different angle, and each relies on `00`: "The graph
does not automatically copy those missing facts onto sparse files."

## NEEDS-JOSEPH (this node only)

- **NJ-PCB-1 — which extractor family owns plain-text CAM formats (Gerber, Excellon, IPC-D-356)?**
  This row lists them as `code_structured`, because `00`'s structured-text path is what actually
  reads their header directives. But by meaning they are CAD outputs, and `00` names CAD files
  under design and creative formats — whose extractor is described as yielding dimensions, canvas
  properties, layers and artboards, none of which a Gerber has until it is rendered. A third
  answer, metadata-only indexing, discards the header evidence this row's strongest signal depends
  on. A routing decision one template must not make alone; the JSON states its choice openly.
- **NJ-PCB-2 — is this row and `engineering.electrical-schematic` one row or two?** They share
  design item, tool, project file and release moment. Two here, because the discriminating
  evidence genuinely differs and a merged row's signals would be the *union*, which is how a row
  stops discriminating. Alternatives: (a) keep two, as written; (b) merge into one
  `engineering.circuit-design` row with schematic-versus-layout as an `engineering_artifact_type`
  value; (c) keep two but declare a shared grouping reason so a project's schematic and layout
  always co-retrieve.
- **NJ-PCB-3 — leg 2 depends on a field R1c may delete.** The dimension argument rests entirely on
  promoting the schema's proposed `revision_or_baseline` to a folder level under the exception the
  schema itself allows. If R1c rejects that key outright under **NJ-ENG-2**, leg 2 collapses, the
  row stands on leg 1 alone, and it should be re-tested rather than quietly kept.
- **NJ-PCB-4 — the scope of the absorbed legacy row.** `soft.hardware-design-file` names a *file*,
  not a release. Read narrowly, this row is a file-format row and **must be refused**. It survives
  only on the roster hint's second clause, "and the manufacturing package produced from it."
  Confirm the wide reading, or refuse the row. This is the single decision the row's existence
  turns on, and it is recorded as a question rather than settled here.
