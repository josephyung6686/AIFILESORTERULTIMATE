## Node test argued in full

**Detection differs.** The schema default is organised around goods custody, a vehicle lifecycle, driver permission or warehouse movement. This template's irreducible structure is a one-to-many ordering: one working date/run allocates named resources across ordered stops, followed by actual statuses against the same order. Delete every domain word; the sequence/resource/plan-actual relation survives. Delete that relation and only an address list or rota remains. Thus this is not a work-type label padded into a row.

**Dimensions differ.** The schema anchor itself states that `logistics.route-dispatch` is the sibling with a real time-first claim because its subject is a working day. Route numbers, vehicles and drivers are reused; the day's resource state supplies their context. Held recommendation is working date → route/run → function. `dimension_order` remains empty because PR-6 declares no schema fields; accepted-group labels carry the concept until R1c adjudicates fields. This avoids inventing a key merely to make a placeholder template look complete.

**Privacy differs.** The route pack exposes where named workers went, when they arrived, deviations, failed-stop explanations, customer addresses and access notes. Its coherent dossier could enable comparative worker profiling. Driver and consignee names and addresses are therefore observations and group context only, never folder dimensions. This is more specific than the schema default's warning against counterparty-shaped folders.

## Reciprocal boundaries and collision fixtures

The JSON edges use the required object shape `{domain, signal, provenance}`. Each signal starts **SAME FIXTURE BOTH SIDES** and names the evidence item that decides which side counts it, so P6 activation step 3 and P8 do not have to infer direction from vague prose.

- Against `construction_property.site-diary`, the identical fixture is `Daily site diary - Block C - 2026-08-27.pdf`. Fixed-site control (project/site, trades, weather, progress) belongs there; ordered mobile execution (route/stop order, allocations, planned versus actual) belongs here. From that side, a vehicle or delivery mention cannot cross the seam; from this side, a date plus vehicles cannot either.
- Against `retail_hospitality.event-production`, the identical fixture is `Event transport schedule - Harbour Gala - 2026-08-27.xlsx`. Programme dependencies, guests/crew and venue zones belong there; delivery/collection route execution belongs here. The purpose of the order, not the vehicle, discriminates.

`also_holds_with` is empty deliberately. CONNECTION restricts it to schema↔schema records; it is not a place for template intent. A route manifest can genuinely support two schemas, but R1c must express that at schema level.

## Neighbours considered without an authored edge

- `business_operations`: a staffing rota, service-call schedule or sales itinerary can share names, dates and addresses. No single landed same-kind row supplied a reciprocal exact fixture, and the route sequence plus logistics execution statuses are sufficient as never-alone boundaries.
- `manufacturing.production-planning`: both allocate resources through time, but production planning orders operations at a fixed production system while this row orders mobile stops. Another session owns manufacturing files, so this row does not speculate or edit their seam.
- `logistics.shipment` and `logistics.last-mile-pod`: these are siblings on the same schema. A shipment record is consignment-level; a POD is stop-level; this row is run/day-level. They can be members of one accepted group without a collision edge or copied facts.
- `calendar`: it is a SOURCE_TYPE, not a roster domain.

## Proposed fields

None. `fields` and `proposed_fields` are both empty. The logistics schema's PR-6 deferral controls. The tempting `route`, `run`, `working_date`, `driver` and `vehicle` keys were not minted. In particular, the same operational identifier might be a route definition, a daily run instance or a consignment, and R1c should decide that boundary once rather than accept a local synonym.
