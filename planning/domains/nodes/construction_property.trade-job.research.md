## What makes this a node rather than a small project

Scale is not usually a good reason for a node, so the argument has to be that scale changes the OBJECT,
and here it does:

- **The anchor changes.** Every other construction row organises by project or property. This one
  organises by client-and-address, because a trade's corpus is a list of customers rather than a list of
  contracts. That is a different `dimension_order` recommendation, which is one of the node test's grounds.
- **The document population changes.** Most files here are machine-generated by field-service software —
  a job sheet with a captured customer signature at the foot. That signature-on-a-work-record pairing
  appears in no other row in the catalogue, so the detection signal is independently distinct.
- **The privacy posture changes.** A project holds commercial material about firms; a job holds a private
  individual's name, home address, phone number, signature and photographs of inside their house,
  multiplied by thousands of customers. That is the third ground, and it is the strongest of the three.

## Files considered and rejected

- **The main-contract valuation.** Kept as the fixture that separates job from project.
- **The quote itself.** Deliberately NOT claimed: `construction_property.quote-estimate` is a sibling row
  and owns the pre-acceptance document. This row claims the quote only as a member of a completed job,
  and the collision entry says so in both directions.
- **The gas safety record.** Kept, but not claimed exclusively — it is `compliance-certificate`'s standing
  property record the moment the job is over, and a landlord's tenancy obligation after that.
- **The trade's own accounts, VAT returns and tax records.** Rejected to `finance.small-business-bookkeeping`.
  The row stops at the invoice.

## proposed_fields

None. Schema declares no field rows (D1 as narrowed, PR-6). Prose candidates: a client key, a property
address key (which every property row wants and which D4 makes delicate, since what varies by jurisdiction
must stay a value), and a job identifier. Not minted.

## Neighbours considered that did NOT get an edge

- `photos` / `finance` (schemas) — real, expressed as `also_schema` on the photograph and invoice file
  examples, because `also_holds_with` joins schemas only and this is a template row.
- `logistics.last-mile-pod` — a proof-of-delivery signature capture is structurally very close to a job
  sheet's signature. Rejected because the discriminating anchors (a consignment, a drop sequence) never
  appear on this row's files, so the edge would have been resemblance rather than confusable evidence.
  Flagged here in case R1c disagrees.
- `retail_hospitality.*` — a service ticket with a customer signature exists there too; not edged for the
  same reason, and because no landed node file exists yet to reciprocate with.
